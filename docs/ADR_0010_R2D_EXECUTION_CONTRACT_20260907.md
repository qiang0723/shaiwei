# ADR 0010：R2D发布执行合同修复（2026-09-07）

状态：工程方案冻结；不授权真实预检、scope生成或生产动作。

## 目标与事实
将Astra三项P1及身份/时效P2落实为执行入口强制门。现有候选不含可信首次写入标记，
宿主查账本无法排除扫描后写入竞态。不得据此继续自动旧版回滚。

## 选择
比较：改候选增加写入握手（需重建与新fixture授权）；宿主扫描（存在竞态，不采用）；
启动派发前持久化保守写入屏障（本次采用）。屏障表示MAY_HAVE_WRITTEN，不冒称已发生首次写入。
派发后任何失败/未知都禁止自动旧版恢复，人工恢复需新协议授权。这满足原写入后禁止回滚门，
并保守收窄写入前自动恢复。候选与scheduler业务代码均不改变。

## 分层与输入输出
新增纯元数据规划/产物投影模块、执行scope与批准合同模块、宿主元数据适配器、薄执行编排模块，
每个新模块不超过400行。复用现有daily.build_plan、发布身份/fixture/受控Git与mount合同。
readiness使用YAML中的daily配置，无dotenv、环境变量或凭据解析；paper只返回身份白名单，
按哈希核验产物并检查FORWARD。镜像仅定向读标签，复用封存fixture运行身份，不在预检新建容器。
容器通过Docker标签查询（不使用会隐式解析.env的compose ps），精确绑定容器ID、重启数与四挂载。

执行scope版本r2d-execution-scope-v1绑定完整协议摘要、配置字节SHA、HEAD/本地origin引用、
控制器组件、候选、旧生产容器与Compose项目标识、state/audit哈希及窗口。批准文件版本
r2d-execution-approval-v1要求scope哈希及精确批准文本一致。文件不是签名认证；
人类批准由受信操作人转录，工具不能自行构造批准冒充用户。威胁模型不防御任意修改代码的宿主所有者。
旧R2D execute入口退役并失败关闭；新入口只允许start，不重复Phase A。低层release原语仍属
操作人受控接口，本合同不宣称能禁止具有任意宿主代码执行权限者直接调用原语。

## 单次消费与失败
独立固定.release/r2d-executions路径，复用storage.interprocess_lock线程/进程双层锁串行化不同scope，
注册唯一local-only发布资源，原子不可覆盖claim防同scope重用。禁止新增直接flock旁路。
此处显式将锁资源注册器及既有锁适配器纳入控制器组件清单；不改变生产锁资源或候选镜像。
合法批准、协议字节/Schema绑定和入口时窗验证后占用claim；预检失败、执行失败、异常、成功均留终态，崩溃仅留claim表示UNKNOWN且不重试。
派发前保存scope/候选/日期绑定的屏障。文件及父目录fsync；符号链接或路径越界失败关闭。
预检与派发前复核动态证据和真实时钟（0≤心跳年龄≤既有3600秒），拒绝未来、过期和控制器漂移。
最终Docker变更前增加时间回调，避免底层启动准备跨窗口；无自动回滚。

## 验收与迁移
仅合成测试：缺批准、改scope/config、并发、重复、崩溃、产物漂移、BACKFILL、旧容器替换/重启、
缺锁卷、未来心跳、跨截止、派发后模拟写入/健康失败、dotenv禁止。运行架构检查、全套测试、Ruff、
差异与脱敏检查。旧配置/receipt/scope不改写；旧组件哈希因工程变化自然失效，不填未来HEAD。
工程完成后只报告新组件清单与身份迁移待办，另行冻结真实配置和生产scope。没有候选重建、
fixture重跑、网络、密钥或真实效果读取授权。若将来需要精确写入前恢复，另立候选握手方案。
