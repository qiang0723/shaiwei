# R2-1R0L-B-R1 Timeline 并发锁恢复协议

- 冻结时间：2026-08-24T21:54:08+08:00
- 合同：`r2-1r0l-b-r1-timeline-lock-recovery-v1`
- 机器真身：`config/r2_1r0l_b_r1_timeline_lock_recovery_v1.yaml`
- 状态：`FROZEN_ENGINEERING_ONLY`
- 生产授权：无

## 1. 问题与目标

R2-1R0L-B 的唯一 Docker bind mount fixture 为 11/12：两个同进程线程并发追加同一 timeline 文件时，
产生两个都引用零哈希的首记录；独立读取在第二行正确失败关闭。失败候选、JUnit、timeline 和输出树
哈希永久保留，同 scope 不重跑。

本节点只恢复 append 临界区的并发串行保证。成功标准不是“测试偶然变绿”，而是把同进程线程互斥与
跨进程文件锁分成两层，并分别用能在旧实现上失败的合成门证明。

## 2. 选择方案

采用“进程内规范路径互斥 + 既有操作系统文件锁”的双层方案：

1. 先按文件规范路径取得进程内互斥；
2. 再打开追加句柄并取得 `flock`；
3. 在双层保护下读取和校验完整既有链，计算前驱，追加、flush、fsync；
4. 释放文件锁后释放进程内互斥；
5. 互斥注册表只保留正在持有或等待的路径，最后一个使用者离开即删除，避免按交易日无限增长。

保留 `flock` 是因为进程内互斥不能覆盖多个 Python 进程；增加进程内互斥是因为 L-B 已证明不能只靠
当前 bind mount 上的 `flock` 语义。两层都不能被其中一层替代。

## 3. 不变边界

- timeline Schema、哈希算法、phase、预算、outcome、通知语义和按启动日跨午夜绑定不变；
- 存储目录、文件名和业务账本权威性不变；
- 不改 scheduler 编排、模型、策略、信号、模拟仓、Web 或生产配置；
- 不读取 `.env`、data、真实业务结果或密钥；
- 不回填、不修复或删除既有 timeline；
- 不修改、覆盖或重跑 R2-1R0L-B 失败产物。

## 4. 工程门

必须同时通过：

1. 进程内路径互斥自身能把同一路径临界区最大并发数限制为 1，并在使用者退出后释放注册项；
2. 即使将测试内 `flock` 替换为无效果函数，多线程写入仍形成一条完整、可验证的链；
3. 多个独立 Python 进程依赖真实 `flock` 写入同一文件，仍形成一条完整、可验证的链；
4. 既有跨午夜、篡改、截断、异常、慢阶段与通知隔离测试不回归；
5. architecture-check、全仓测试、Ruff、compileall、pip check、diff-check 与脱敏检查通过。

restart、真实业务运行、历史回填、生产账本写入均为 0。
