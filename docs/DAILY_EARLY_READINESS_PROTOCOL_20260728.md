# 日增量16:00早探测协议

> 日期：2026-07-28（Asia/Shanghai）
>
> 协议：`p0-daily-early-readiness-v1`
>
> 状态：`FROZEN_BEFORE_IMPLEMENTATION`

## 目标

把A股日增量由“19:30后才首次接纳当日”改为“16:00开始探测，数据齐全即正式跑”，同时避免把
提供方尚未入库当成生产故障，也避免不完整响应进入不可变raw、账本、信号或模拟仓。

## 外部时点证据

Tushare官方资料在冻结日给出的口径为：

- A股日线 `daily`：交易日15:00—16:00之间入库；
- 每日指标 `daily_basic`：交易日15:00—17:00之间更新；
- 股票/指数行情总口径：通常15:00—17:00；
- 复权因子 `adj_factor`：当日盘前入库；
- 停复牌 `suspend_d`：不定期更新。

来源：

- <https://tushare.pro/document/1?doc_id=27>
- <https://tushare.pro/document/2?doc_id=32>
- <https://tushare.pro/document/1?doc_id=109>
- <https://tushare.pro/document/2?doc_id=28>
- <https://tushare.pro/document/2?doc_id=214>

因此16:00只能是最早探测点，不能预注册为稳定完成点。

## 冻结行为

1. scheduler继续每15分钟对账；北京时间16:00前，当日不进入计划。
2. 16:00—19:29之间，如果缺失项仅包含当日交易日，先查询正式五类输入：`daily`、`adj_factor`、
   `daily_basic`、`suspend_d`、中证800 `index_daily`。
3. 探测必须复用正式请求字段、Tushare响应规范化和 `validate_trade_date` 完整性门，包括日期、唯一键、
   全市场最低行数、行情对子因子/每日指标覆盖、基准唯一行和 `.BJ=0`。
4. 探测只保存在内存；不得调用 `RawBatchWriter`，不得写raw、ingest ledger、daily ledger、通知ledger、
   信号、模型、模拟仓或研究产物。
5. 数据未齐、提供方暂时空表或临时请求错误统一返回 `WAITING_SOURCE`；不写FAIL、不发飞书失败告警。
   scheduler健康文件只记录脱敏状态和目标日期，不记录provider原文或凭据。
6. 探测一旦通过，立即执行原有正式日增量路径；正式路径仍重新请求并写不可变批次，再以账本中的
   真身通过同一完整性门，不能把内存探测结果直接当生产数据。
7. 北京时间19:30起不再以“来源可能未齐”静默等待；执行原正式路径。任何失败继续写FAIL、发飞书
   告警并使scheduler降级，保持现有异常发现上界。
8. 历史缺口补采不走当日早探测，仍按最早缺口顺序立即执行；休眠唤醒和最多20个交易日规则不变。

## 非目标

- 不保证每日恰好16:00完成；真实完成时点由提供方数据齐备决定；
- 不调整字段、最小行数、北交所排除、质量哨兵、信号截止或模拟仓执行规则；
- 不用其他数据源填补Tushare暂未入库；
- 不把探测失败计作生产成功、失败或研究证据；
- 不与Top20首次生产调度切换合并发布。

## 验收门

- 单测覆盖15:59不接纳、16:00进入早探测、未齐零写入/零通知、就绪进入原正式路径、19:30恢复原
  fail-closed路径、历史缺口不等待；
- Python全仓、Ruff、compile、配置测试和 `git diff --check` 通过；
- Docker断网fixture证明未齐探测不产生业务文件变化；
- 构建独立不可变scheduler候选，但只在Top20首发验收结束后的新交易日窗口受控切换；
- 切换后至少核验一个真实交易日的首次探测时点、正式完成时点、整日PASS、`.BJ=0`、信号/模拟仓、
  飞书和幂等证据。

全部工程门通过只能得出 `GO_EARLY_READINESS_ENGINEERING_ONLY`；真实16:00稳定性需日后按观测统计，
不得由单日成功外推。
