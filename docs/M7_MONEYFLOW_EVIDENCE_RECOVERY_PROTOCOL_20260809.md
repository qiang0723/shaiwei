# M7-0R3 资金流证据双轨恢复协议（结果已知，protocol-only）

## 1. 本节点裁决

本节点冻结 `m7-moneyflow-evidence-recovery-v1`，只把 M7-0R2 已经暴露的两类缺口转成可施工、
可独立审计的恢复合同：

1. **轨 A：908 条停牌证据缺口。** 对
   `PRIMARY_FULL_DAY_SUSPENSION_ONLY_UNRESOLVED` 的精确键，使用既有 Baostock
   `history_k_data_plus` 的 `tradestatus` 做独立状态核验。
2. **轨 B：541 条主源资金流缺键。** 对
   `CONFIRMED_MONEYFLOW_GAP_DAILY_PRESENT` 的去重源键，只从同语义的 Tushare
   `moneyflow` 重新取证，并要求“按交易日全市场”和“按证券单日”两种请求形态逐键一致。

当前只冻结协议和机器断言：不读取真实证券键，不调用外网，不读取资金流数值，不物化恢复批次，
不计算调整后覆盖率，也不进入候选、标签、收益、模型、回测、前瞻、模拟仓或生产。

## 2. 为什么分成两条轨道

M7-0R2 已将 757,636 个成员日中的 2,615 条资金流缺口完整分区。1,157 条来自已冻结隔离日，
9 条已有独立未交易证据；真正需要补证的只有：

- 908 条：Tushare `suspend_d` 表示全天停牌、日线也缺失，但没有独立交易状态；
- 541 条：日线存在，说明当日存在正常行情事实，但主 `moneyflow` 没有对应键。

这两者的证据问题不同。轨 A 要回答“当日是否确实未交易”；轨 B 要回答“主源是否能以同一业务口径
返回漏掉的资金流记录”。两者不能用同一种填充规则，也不能在一个模糊的“覆盖率修复”步骤中混合处理。

## 3. 最小补救原则

### 3.1 轨 A 复用现有独立源

仓库已有 Baostock 状态采集器，但现有通用 S1/S6 计划器只为“无日线且没有主源全天停牌证据”及
“日线与停牌证据冲突”生成请求；它没有查询“主源已报全天停牌且日线缺失”的精确键。因此 908 条未决
不能解释为 Baostock 已经证明无覆盖。

R3 使用一个恢复专用的窄计划器，只计划这 908 条已封存键，不改变通用 S1/S6 行为：

- `trade_status=0` 且日线缺失：独立确认未交易；
- `trade_status=1`：与主源全天停牌/日线缺失冲突，失败关闭；
- 缺行、非法状态或多行冲突：保持未决，失败关闭；
- 禁止前填、后填、相邻日期推断或把主源自己的 `suspend_d` 当独立复核。

当前不新增上交所公告归档解析器。新增运行时官方网页源会引入新的抓取、解析、版本和可追溯合同；应先
验证既有独立源能否覆盖精确 908 键。若仍有剩余，再另立协议和 ADR，而不是在本轮提前扩张。

### 3.2 轨 B 只接受原 `moneyflow` 语义

Tushare 官方文档允许 `moneyflow` 既按 `trade_date` 取全市场，也按 `ts_code + start_date/end_date`
查询，并规定单次最多返回 6,000 行。R3 对每个去重缺口键都要求两种请求形态返回同一规范化 20 字段行；
单边缺失、双边缺失或内容不同分别记为明确冲突，不能静默择新、择多数或只取有值的一边。

官方的 `moneyflow_ths` 和 `moneyflow_dc` 使用不同的数据提供方和字段/分类语义，不是主
`moneyflow` 的可互换副本，因此本轮禁止拿它们补洞。也禁止零填充，或用日线 `amount/volume`
反推主动买卖资金流。

参考的官方口径：

- [Tushare 个股资金流 moneyflow](https://tushare.pro/document/2?doc_id=170)
- [Tushare 停复牌 suspend_d](https://tushare.pro/document/2?doc_id=214)
- [Tushare 日线 daily](https://tushare.pro/document/1?doc_id=27)
- [Tushare 同花顺资金流 moneyflow_ths](https://tushare.pro/document/2?doc_id=348)

## 4. 调用上限和一次性语义

当前协议不授权任何真实调用，只冻结未来 release 的最坏上限：

- 轨 A：最多 908 个 Baostock 请求；允许按证券合并有界日期窗，但输出必须精确回投目标日期；
- 轨 B：最多 541 个全市场日期请求和 541 个单证券单日请求；
- 两轨合计最多 1,990 个 provider 请求，全部串行；
- 每个请求在首发前写入不可变 claim；传输级尝试最多 3 次，语义空响应不重试；
- 部分失败只能继续从从未 claim 的请求开始，已 claim 的失败请求不得在同一 release 重发；
- 原始响应追加写入并绑定请求身份、行数和内容 SHA-256，密钥不得出现在命令、日志、报告或 Git。

这使网络闪断和“看到缺口后再反复请求直到有值”具有不同且可审计的处理方式。

## 5. 数据质量与决策门

预期粒度冻结为“源日期 × 证券”，再投影回三个股票池的成员行。完整性、唯一性、合法性、一致性、
引用完整性和时点约束必须同时核验，并按股票池与半年分段报告。冲突与未决必须分列，不能合并成一个
看似较小的异常率。

只有以下条件全部成立，才可裁
`GO_M7_EVIDENCE_RECOVERY_DATA_ONLY`：

1. 上游协议、scope、manifest、core hash 和精确分区身份一致；
2. 轨 A 的 908 条全部取得终态，且冲突与未决均为 0；
3. 轨 B 的全部去重键均由主 `moneyflow` 两种请求形态返回，规范行内容一致；
4. 无额外键、重复键、`.BJ`、非法字段、非有限数、6,000 行饱和响应或不可变批次损坏；
5. 内部重放和独立实现审计逐字段一致。

任一轨失败，整体只能裁 `NO_GO_M7_EVIDENCE_RECOVERY_INCOMPLETE`，但两轨状态仍分别报告。
不允许“一条轨 GO 就先进入候选”。

## 6. 不改变什么

- 原 M7 `NO_GO_M7_0_DATA_COMPATIBILITY` 和 R2
  `NO_GO_M7_GAP_LINEAGE_INCOMPLETE` 永久保留；
- 原三池、PIT 映射、隔离日、分母和 99.5%/99%/95% 三层门槛不变；
- 本节点及未来恢复 collection GO 都不计算或宣称调整后覆盖率；
- 即使恢复数据全部通过，也必须再立 successor M7 数据门，用原口径重算后才能讨论八候选；
- `strategy_effective=NOT_EVALUATED`、研究尝试增量 0、生产授权 none。

## 7. 下一停止点

本协议提交并推送后停止。下一目标只能施工 synthetic-only 工程门：恢复专用计划器、双形态一致性
校验、claim/断点语义、内部重放和独立审计 fixture。工程实现推送并生成精确 release scope 后，才可请用户
另行绑定 scope 批准真实网络采集；任何旧 M7/R2 approval 都不能复用。
