# ADR-0007：TS proposal 的本地权威绑定与搜索预算归属

- 日期：2026-08-13
- 状态：Accepted
- 适用范围：TS-v5候选生成的proposal输入合同
- 决策依据：R3D `STOP_LOCAL_IMPLEMENTATION_DEFECT`

## 问题与结果目标

proposal v2把尝试模式、父候选和每个参数的搜索点数交给LLM填写，但批准scope、runner记账和最终搜索
预算又由本地系统控制。这形成两个权威来源：R3C六个批准的独立席位全部返回反方模式，而runner仍按
独立模式记账；5/6回答自行组合出的搜索积还超过冻结上限196。

目标是让未来候选的研究语义仍可由LLM提出，但授权身份和计算预算只能来自结果前冻结的本地事实，
并让请求、Schema、编译产物和证据使用同一权威。

## 备选方案

1. **继续由LLM填写，编译时比对。** 改动最小，但仍把不应由模型决定的字段暴露给模型，增加失败率，
   且请求与账本之间仍需维护两份表达。
2. **在Schema中把模式固定为单值、搜索点设固定常量。** 能关闭本次独立席位缺陷，但未来反方席位仍需
   动态改Schema，搜索点按槽位数量变化时容易再次复制规则。
3. **本地权威注入（采用）。** proposal响应完全移除lineage和搜索点；编译器从验证后的AttemptPlan注入
   lineage，并按槽位数机械分配搜索点。证据模式只从编译候选派生。

## 决策与代价

采用方案3，新增`ts-v5-mechanism-proposal-v3`，保持v2和最终`MechanismCandidate`字节不变。v3请求包含
只读的`assigned_attempt_authority`供模型理解上下文，但响应Schema不接受同名字段。搜索点采用冻结的
1→7、2→7、3→5、4→3、5→2同槽分配，编译后仍由原validator重算196上限。

代价是proposal v2与v3需要并存，历史复算继续使用v2；未来反方研究不能复用本独立合同，必须用含唯一
父候选的结果前scope另立版本。这个额外版本成本换取单一权威、失败关闭和清晰审计。

## 依赖、数据和权限边界

新模块属于研究领域合同层，只依赖既有候选模型和冻结研究常量，不依赖HTTP、Docker、Web、`.env`或
生产编排。R3E只离线读取R3C封存响应作拒绝重放，不读取reasoning、行情、证券、收益或secret，不写
生产账本。

## 迁移、回滚与退出

- v2继续作为R3B/R3C历史复算真身，不迁移或改写旧响应、账本和裁决。
- 未来live runner只有在新scope/release获批后才能切到v3；R3E本身不切换任何live或生产入口。
- R3E失败时回滚方式是停止使用v3新增模块，v2历史能力不受影响；失败证据保留。
- 当所有仍需复算的v2批次均有永久封存镜像/证据且没有新调用依赖v2时，才可另立目标评估退出v2，
  不在本ADR中自动删除。

## 验收与复审触发器

验收必须覆盖六机制合成编译、1—5槽搜索积、模式不可覆盖、额外字段/跨机制/文本/范围等对抗失败、
R3C六份旧响应0录取、独立audit、write-once幂等、旧合同与validator哈希不变。

如未来出现以下任一情况，必须复审：需要反方或多父候选席位；搜索空间不再是笛卡尔积；参数槽超过5；
最终候选validator改变；或证据需要在编译前登记不同于候选lineage的模式。
